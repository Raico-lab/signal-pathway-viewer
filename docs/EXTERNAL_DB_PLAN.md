> 計画の `data/source.json` は `data/server.json` という名前にした。日本語訳の共有（取り込みと送信）も加えた（2026-10-07 に廃止）。
> 2026-10-03 の方針: **地図で使う DB はローカル、情報源（論文・サイト）の情報はサーバーの DB を正とする**（§10）。

> 現在は DB をアプリに同梱し、各 PC のローカルにコピーして使っている（[README](../README.md#データの保存場所)）。
> 今後、無料の外部サーバーから DB を配信する可能性があるため、そのときの方針と動線をここに定めておく。

## 1. 目的

- アプリを再配布しなくても、最新の DB を各 PC に届けられるようにする。
- オフラインや、サーバーが止まっているときでも、手元のデータで今までどおり使えるようにする。

## 2. 基本方針

**アプリは常にローカルの DB を読む。サーバーは「新しい DB を届ける経路」としてだけ使う。**

現在の「同梱 DB → ローカルへコピー」という仕組みに、「サーバー → ローカルへコピー」という経路を 1 本足す形にする。
可視化やシミュレーションの処理はローカルの SQLite を読むだけなので、サーバー対応の影響は受けない。

```
 [同梱 DB (data/)] ──┐
                     ├─(新しければ確認→バックアップ→置き換え)─→ [ローカル DB] ─→ アプリの全機能
 [外部サーバー]  ────┘
```

この方針にする理由:

- DB は基本的に編集しない運用なので、「最新版を配る」だけで足りる。
- 無料サーバーは停止や仕様変更が起こりやすい。サーバーに常時つなぐ設計にすると、そのたびにアプリが使えなくなる。
- 現在のコード（`tor_app/datastore.py`）の仕組みがそのまま使える。

## 3. サーバーの候補

| 候補 | 仕組み | 向いている場合 | 注意点 |
|---|---|---|---|
| **GitHub Releases / リポジトリの静的ファイル**（推奨） | DB ファイルと案内ファイル（`manifest.json`）を置き、アプリがダウンロードする | 配布だけでよい場合（現在の運用） | 公開リポジトリだと DB が誰でも見られる。未発表データを含むなら非公開リポジトリにし、読み取り専用のトークンが必要 |
| Google ドライブ / Dropbox の共有リンク | 同上（直接ダウンロードできるリンクを使う） | 研究室ですでに使っている場合 | リンクの形式が変わることがある。大きいファイルでは確認画面が挟まることがある |
| Supabase など（無料の PostgreSQL） | サーバー上の DB を直接読み書きする | 複数人がアプリから同時に編集したくなった場合 | 無料枠には「一定期間アクセスがないと停止」などの制限があることが多い（採用時に最新の条件を確認する）。アクセス制御の設定が必須 |

まずは静的ファイル配信で始める。アプリからの共同編集が必要になった時点で、Supabase などを検討する。

## 4. 配信するファイル

サーバーには次の 2 つを置く。

- `tor_pathway.db`: `tools/build_db.py` で作った DB（同梱用と同じもの）
- `manifest.json`: DB の版を示す案内ファイル

```json
{
  "data_version": "2026-10-15",
  "schema_version": 1,
  "sha256": "（tor_pathway.db のハッシュ）",
  "url": "https://…/tor_pathway.db",
  "notes": "GLN3 標的遺伝子を追加"
}
```

- `data_version`: 利用者に見せる版名。確認画面や画面下のステータスバーに表示する。
- `schema_version`: テーブル構造の版。アプリが対応していない値なら取り込まずに「アプリを更新してください」と表示する。
- `sha256`: ダウンロードしたファイルが壊れていないかの確認に使う。

### 容量について

対象を全遺伝子に広げたため、DB は数十 MB 以上になりうる。GitHub のリポジトリには 1 ファイル 100 MB を超えるファイルを置けないので、大きくなったら Releases の添付ファイルとして置く（採用時に最新の制限を確認する）。ダウンロード中は進み具合を表示する。

## 5. 利用者の動線

### 起動時（自動）

1. ローカル DB で**すぐに画面を表示する**（サーバーの応答を待たない）。
2. 裏で `manifest.json` を取得する（タイムアウト 5 秒程度）。
3. 結果に応じて、次のように振る舞う。

| 状況 | アプリの動き |
|---|---|
| 手元が最新 | 何もしない。ステータスバーに「データ: 2026-10-15版（最新）」 |
| 新しい版がある | 画面上部に案内を表示: 「新しいデータ（2026-10-20版: GLN3 標的遺伝子を追加）があります [更新する] [後で]」 |
| つながらない | 何もしない。ステータスバーに「オフライン（手元のデータで表示中）」 |
| アプリが古くて対応できない | 案内を表示: 「新しいデータを使うにはアプリの更新が必要です」 |

起動のたびにダイアログを出さず、画面上部の案内だけにする。邪魔にならないようにするため。

### 「更新する」を押したとき

1. 一時ファイルにダウンロードする。
2. `sha256` を照合し、SQLite として開けるか、テーブルがそろっているかを確認する。
3. 現在のローカル DB を `backups/` に保存する（今の仕組みと同じ）。
4. ローカル DB を置き換え、画面を読み直す。
5. どこかで失敗したら置き換えずに、元のデータのまま理由を表示する。

ローカルで編集していた場合は、確認画面で「この PC での変更は上書きされます（バックアップされます）」と明示する。

### メニュー（手動）

- 「ファイル > 最新データを確認」: 起動時と同じ確認をその場で行う。
- 「ファイル > 同梱データに戻す」: 既存。サーバーが使えなくなったときの最後の手段にもなる。
- 「ヘルプ > データの情報」: 今使っているデータの版と取得元（同梱かサーバーか）、取得日時を表示する。

## 6. データ管理者の動線

1. DB を編集する（CSV を直すか、手元のアプリで編集して CSV エクスポートする）。
2. `python tools/build_db.py proteins.csv interactions.csv` で DB を作る。
3. `manifest.json` を作る（ハッシュと版名を書く。将来 `tools/` にスクリプトを用意する）。
4. DB と `manifest.json` をサーバーに置く。
5. 利用者の PC では、次回起動時に「新しいデータがあります」と表示される。

アプリを再配布するときは、同じ DB を `data/` にも入れておく。そうすれば、新しく配布を受けた人はオフラインでも最新版から始められる。

## 7. 実装するときの変更箇所

| 箇所 | 変更内容 |
|---|---|
| `data/source.json`（新規） | 取得先 `manifest.json` の URL と、サーバー配信の有効・無効を書く。アプリに同梱し、利用者には設定させない |
| `tor_app/datastore.py` | `install_bundled()` と同じ流れで、サーバーから取得する処理を追加する。「最後に取り込んだもの」の記録（`bundle.json`）に、取得元・版名・取得日時を加える |
| `tor_app/ui/main_window.py` | 起動後に裏で版を確認する処理、画面上部の案内、上記メニューを追加する |
| `tor_app/db/models.py` | `meta` テーブルを追加し、`schema_version` と `data_version` を DB 自体に記録する |
| `tools/` | `manifest.json` を作るスクリプトを追加する |

可視化タブ・DB 管理タブ・シミュレーションは変更不要。

## 8. 決めておくこと（サーバーを選ぶとき）

- DB に未発表データが含まれるか → 公開の置き場所を使ってよいかが決まる。
- 利用者がアプリから DB を編集する必要があるか → 静的配信で足りるか、Supabase などが必要かが決まる。
- 研究室のネットワークから、その外部サービスにつながるか（学内のファイアウォール）。

## 9. 日本語訳の共有（2026-10-03 追加。2026-10-07 に廃止）

> 機械翻訳（Google 翻訳の非公式の窓口）は、公開版の利用規約の問題があるため、訳の共有ごと廃止した。以下は当時の計画。

- サーバーに `translations_ja.json`（英語の原文 → 訳）を置く。アプリは起動時に取り込み、手元にない原文の訳だけ加える。
- アプリで新しく訳したものは `translations_pending.json` に貯め、起動時に `POST {base_url}/translations`
  （本文 `{"translations": {原文: 訳}}`）で送る。送れたら消す。送れなければ次の起動で送り直す。
- 受け取り口は静的ファイルの置き場所では作れないので、小さな API（Cloudflare Workers・Supabase など）が要る。
  集めた訳を確かめて `translations_ja.json` に足す流れはサーバー側で決める。
- Google 翻訳の非公式の窓口の訳を集めて配ることは、利用規約上問題になりうる。公開する前に、公式の Cloud Translation API に
  切り替えるか、訳の扱いを確かめる。

## 10. データの置き場所の分担（2026-10-03 の方針）

| データ | 置き場所 | 理由 |
|---|---|---|
| 地図で使う DB（遺伝子・関係・カテゴリ。`tor_pathway.db`） | **ローカル**（同梱 → PC へコピー。新しい版はサーバーから配信） | 地図の計算は毎回 DB 全体を読む。手元にあれば速く、オフラインでも使える。利用者の編集も手元に残せる |
| 情報源の論文・サイトの情報（`papers.json`・`sources.json`） | **サーバーの DB**（アプリは書き出したものを読む） | 論文は増え続け、題名・著者・URL の訂正もサーバーで 1 回直せば全員に届く。PubMed の新着監視などもサーバーで回せる |

- アプリ側の実装（済み）: `server.fetch_json()` が `{base_url}/papers.json`・`sources.json` を取り、写しを
  `server_cache/` に保存する。情報源タブは、取れるまでは写し（なければ同梱の `data/` のファイル）を使い、取れたら出し直す。
- 根拠の本数（その論文が根拠になっている関係の数）は、ローカルの地図の DB の根拠欄から数える（今と同じ）。
  サーバーは論文の書誌だけを持ち、関係の本数は持たない。
- サーバー側: 論文の表（PMID・題名・書誌・URL・使い道）を DB に持ち、`papers.json` の形で返す口を作る。
  `tools/fetch_paper_list.py` の処理をサーバーで定期的に回す形にする。

## 11. Web アプリ化（将来）

デスクトップに入れなくても、ブラウザで開くだけで使えるようにする。今の作りのうち、そのまま使える部分と作り直す部分:

| 部分 | 今 | Web 版 |
|---|---|---|
| 地図の描画（`tor_app/web/network.js`・Cytoscape.js） | QWebEngine の中のページ | **そのまま使う**。Python への通知（QWebChannel の `bridge`）を、サーバーへの通信に置き換える |
| 地図の計算（`graph_data.py`・`subgraph.py`・`relation_paths.py` など） | Python（画面の部品に依存しない） | **そのまま使う**。サーバー（FastAPI など）で動かし、地図の要素を JSON で返す |
| 左のタブ・説明欄・データベース・情報源の画面（PyQt） | Qt の部品 | **作り直す**（HTML。説明欄はもともと HTML なので中身は流用できる） |
| 表示の保存（`view.json` など） | PC のファイル | ブラウザの保存領域、またはログインした人ごとにサーバーへ |

地図の DB の扱い（§10 との関係）:
- Web 版では「ローカル」はサーバーの中になる。配信する DB を読むだけの版として持ち、全員で共有する。
- 利用者の編集を残すなら、「全員共通の DB ＋ その人の変更分」をアカウントごとに持つ。最初は閲覧専用にする。
- サーバーに置かずにブラウザだけで動かす案（SQLite の WASM 版・Pyodide で Python を動かす）もあるが、
  DB が 20 MB あり読み込みが重く、計算も遅くなるので、まずはサーバーで計算する形を勧める。

今のうちに守っておくこと（Web 版に移しやすくするため）:
- 地図の計算は `tor_app/ui/` に書かず、画面の部品に依存しないところ（`tor_app/*.py`）に置く。
- 説明欄の HTML を作る処理は、Qt に依存しない関数にしておく。
- JS と Python のやりとりは `bridge` の決まった口（onNodeClicked など）だけにする。
